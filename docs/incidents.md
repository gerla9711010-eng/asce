## 貫穿全部事故的三句話

1. **流程回報成功 ≠ 事情做到了。** FB 回 500 貼文其實發出去了、n8n 執行 success 但節點錯誤被吞掉、
   LINE 回 500 通知沒送到——判斷「寫入到底成功沒」不要只看有沒有噴錯。
2. **保底邏輯只要「讓流程繼續」而不管「送出去的東西對不對」，它就是在把故障洗成看起來成功的樣子。**
   對外送出的東西一律要有形狀檢查。
3. **改完沒有在「真正在跑的環境」實地驗一次 = 沒改。** 補防護一律要有一次可觀察的實測
   （例如真的收到一則 LINE），不能只看程式碼寫對了。

## 2026-08-07 ─ 兩天內 4 件廣告被誤擋，2 個獨立 bug（已修）

**症狀**：使用者反映 08-06、08-07 連續有廣告被攔截。查 n8n executions 抓到 4 件：

⚠️ 下面時間全部是**台灣時間**（n8n 執行紀錄本身存的是 UTC，查資料時忘記 +8，事後才發現整批寫錯，已訂正）。

| 時間 | 物件 | 擋的機制 | 原因 |
|---|---|---|---|
| 08-06 11:00 | YG0137742 | 數字守門員 | 查無出處的數字「113」——KEIS 賣點原文寫的是全形「１１３年更換電梯」，AI 產文案轉半形「113」，比對用的正則只認半形，兩邊對不上 |
| 08-06 11:00 | AG1863917 | 數字守門員 | 不該提「學區」——案名本身叫「鳳翔**學區**/全新最強2+1房」，AI 把案名帶進標題，學區欄位卻是空的 |
| 08-07 11:00 | EG0530884 | 文案交叉審核（08-06才上線） | 格局寫「透天廠房」，官方格局欄位是空的、賣點原文完全沒提——**這件是真的誤擋，AI 憑空編造，機制抓對了** |
| 08-07 13:00 | AA1044536 | 文案交叉審核 | verdict=NG，但 reason 原文自己寫「這屬於官方資料矛盾，不應由我判斷為NG。我應放行」——AI 自己推翻了自己的判定，verdict 欄位卻沒跟著改 |

**AA1044536 的成因**：審核 prompt 要求回傳 `{"verdict":"OK或NG","reason":"..."}`，verdict 排在 reason **前面**。
`文案交叉審核` 節點用的是 `gemini-2.5-flash` 且 `thinkingConfig.thinkingBudget: 0`（關閉思考，2026-08-04 那次 output token 被思考吃光的教訓），
模型必須逐字直接生成 JSON、沒有「先想後答」的空間，於是先吐出 verdict 才想清楚，reason 寫到一半想通了却已經來不及改前面的 verdict。

**YG0137742 的成因**：`數字守門員` 建事實庫時用 `raw.match(/\d+(?:\.\d+)?/g)` 只認半形阿拉伯數字，KEIS 原始賣點文字裡的全形數字（１１３）完全掃不到，
所以「113」這個數字永遠進不了 `facts` 集合——即使它明明就寫在官方賣點原文裡。

**怎麼修**（3 個都推上線了，`yc-v3-scan-publish` 已 deactivate+activate）：
1. `文案交叉審核` prompt 改成 reason 放在 verdict **前面**，並加一句「reason 裡出現『應該放行/不該擋』，verdict 就必須填 OK」，強制先想清楚再下結論
2. `Gemini 產文案` prompt 加一句：學區欄位空的時候文案全文（含標題）不准出現「學區」兩字，**就算案名/社區名稱本身帶學區字樣也要避開**——不是修守門員放寬標準，是從源頭不讓 AI 寫
3. `數字守門員` 加 `toHalf()` 把全形數字轉半形再比對，KEIS 原文裡的全形數字現在算數了

**沒有動的**：EG0530884 那件——AI 真的憑空編造格局，交叉審核抓對了，不是 bug。

**後續（同一天稍晚）**：2026-07-30 診斷出的 3 個守門員誤判也一起修完了，見下一則。

**學到什麼**：LLM 結構化輸出的欄位順序不是排版問題——關掉思考預算（thinkingBudget:0）的模型是逐字生成，
「先問結論、後問理由」的 schema 會逼它來不及反悔。這類審核 prompt 一律要 reason-before-verdict。
另外：任何「跟官方文字比對」的檢查，都要想到 KEIS 原始資料可能用全形數字/標點，程式這邊只認半形是常見漏洞。

## 2026-08-05 ─ 下架偵測的「二次確認」早就恆真：`來源連結` 存的是會過期的 houseol 網址

**真正的風險**（不是網址醜而已）：線 B 對「沒有 `KEIS廣告ID` 的 v2 舊資料」的雙重確認是

**學到什麼**：**欄位換了資料來源，就要換名字或當場改掉欄位說明。**

另外：只要有「兩個條件都成立才動手」的保險，就要定期驗那兩個條件**是不是還有分辨力**。

## 2026-08-04 ─ 下架偵測對沒貼文的舊資料照樣打 FB DELETE，被靜默失敗巡邏抓到

**症狀**：靜默失敗巡邏 LINE 告警：下架偵測線 `FB 刪貼文`（執行 #4887）回
`Unsupported delete request`，但整條執行狀態仍是「成功」（節點設了 `neverError`）。

**查證**：命中的是 YE0095535（`其他待辦` 早就記著的 3 筆 v2 舊資料之一，Notion 沒存
`粉專貼文連結`，`KEIS廣告ID` 也是空的）。那天它的 houseol 來源連結終於回 404，觸發下架判定。
Notion／KEIS 三邊事後核對**沒有壞資料**：Notion 正確標成「下架」，KEIS 本來就沒有這筆廣告，
沒有任何貼文被誤刪或誤留。

**成因**：`備妥刪文` 不管有沒有貼文連結，一律接去 `FB 刪貼文`。沒有 `fbPostId` 時
URL 變成 `graph.facebook.com/v21.0/`（空 ID），FB 當然回 `Unsupported delete request`。
下游 `判定刪除結果` 靠 `hasFbPost` 判斷要不要理會這個回應，所以結果沒錯，
但**每次處理沒有貼文的舊資料，都會白打一次注定失敗的 API、噴一次會被巡邏抓到的錯誤**——
不是資料事故，是雜訊源，放著不管會讓「靜默失敗巡邏」的訊噪比越來越差。

**怎麼修**：`yc-v3-removal.json` 加一個 IF 節點「有貼文可刪?」，`hasFbPost` 為否時直接跳過
`FB 刪貼文`、接去 `判定刪除結果`（該節點在無貼文分支本來就不讀 FB 回應，繞過去不影響邏輯）。
兩條分支各寫一版隔離測試驗證過（無貼文＝直接判定完成、有貼文＝迴歸正常），已部署
（deactivate+activate 過）。

**學到什麼**：`neverError` + 下游自己判斷成功失敗，是刻意的設計（單筆失敗不能拖垮整批），
但**不代表上游可以隨便亂打注定失敗的請求**——已知會失敗的呼叫要在源頭擋掉，不要靠下游
「反正看得懂這個錯誤」來擦屁股，不然巡邏機制遲早會被這類已知噪音淹沒，真正的新錯誤反而不顯眼。

   （deactivate+activate 過）。

**學到什麼**：
1. **修比對邏輯只保護未來的新資料，不會回頭清洗已經產生的舊資料**——這類 bug 要主動去查
   「這個邏輯上線之前建的案子」還有沒有殘留，不能假設修完就沒事了。
2. **「查得到就填」不等於「填了合理」**：光靠「有沒有比對成功」判斷該不該用一個欄位不夠，
   物件類型本身能不能有這個屬性，要單獨查，不能靠比對邏輯間接擋掉。

## 2026-08-04 ─ 測試打爆 Gemini 每日配額，弄掛 11:00 那班廣告

**症狀**：11:00 班（execution 4725）在 `Gemini 產文案` 失敗，訊息
`The service is receiving too many requests from you`。

**成因**：我（Claude）在開發「文案交叉審核」時，用臨時 webhook workflow 連續打了約 50 次 Gemini，
把當天的配額吃光。**這支金鑰是免費方案，`gemini-2.5-flash-lite` 每天只有 20 次**

## 2026-07-30 ─ 買方配案登入態被 OneDrive 弄掉

profile 放在 `桌面\工具\買方配案\chrome_profile` 時被 OneDrive 同步（5943 檔／4.75 GB），
連 Cookies 檔都變成雲端佔位檔 → Chrome 關著時被改成「線上檔案」＝隔天被登出。

**修法**：登入態搬到 `%LOCALAPPDATA%\buyer-match-chrome`，用環境變數 `BUYER_MATCH_PROFILE_DIR` 指定。
⚠️ 舊的 `chrome_profile/` 還留在 OneDrive 裡沒刪（4.75 GB，確認新的沒問題後可以刪掉停止同步）。
⚠️ **不要硬殺那個 Chrome**（cookie 是關閉時才寫回磁碟，硬殺＝自己製造登出）。

**登入態壽命實測**：房地 `sessionid` 是持久 cookie、約 29 天，關瀏覽器不會掉；
i智慧 的登入 cookie 全是 session cookie（Chrome 一關就沒）、`token` 只活 12 分鐘 →
所以 i智慧 每次都要重登（有帳密會自動處理），這不是工具的問題，是永慶 SSO 的設計。

⚠️ **房地只能手機掃 QR Code 登入，沒有帳號密碼**（2026-07-30 使用者確認），
所以自動重登這條路天生不存在，永遠只能偵測+推 LINE 喊人。
