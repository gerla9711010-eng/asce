## 2026-09-23｜待聯絡提醒整包推不出去：客戶姓名叫「*小姐」

**症狀**：09-23 09:00 排程跑到 `Telegram 告警` 節點 400 失敗（execution 11151），LINE/Telegram
只收到「Bad request - please check your parameters」，當天 20 幾筆待聯絡提醒全部沒送出。

**成因**：n8n Telegram 節點沒設 `parse_mode` 時預設走 **Markdown**。名單裡有一筆客戶姓名是
`*小姐`，單獨一個 `*` 讓 Telegram 解析不到結尾。API 撈執行紀錄才看得到真正的錯誤訊息：
`can't parse entities: Can't find end of the entity starting at byte offset 2346`
——n8n 畫面上那句 Bad request 是通用訊息，看它會找錯方向。

**怎麼修**（PR 見 commit）：
1. `Telegram 告警` 節點 `additionalFields.parse_mode = HTML`（訊息本來就沒用粗體斜體，外觀不變）
2. `組訊息（標重複）` 最後把 `& < >` 轉義（`&` 要先換否則二次轉義）
3. PUT 回 n8n 後 deactivate + activate（排程線必做，否則跑舊版）

**同日已全面掃完**：`scripts/n8n_telegram_html.py --fix` 把線上 **16 個 Telegram 節點**全部改成
HTML 模式，13 個上游 code 節點多產一個 `_tg`（＝轉義過的訊息），Telegram 節點只讀 `_tg`
（不覆蓋原本的 `text`/`summaryText`，才不會影響 LINE 回覆、寫 Notion 那些去處）。
7 支 active workflow 都 deactivate+activate 過。同一支腳本不帶參數就是體檢，已接進
`n8n_sync.py`，以後每次同步都會檢查，不合規會在 `n8n-live.md` 的「分岔檢查」報出來。

**學到什麼**：
1. 客戶姓名/備註是使用者輸入，**任何把它塞進 Telegram 的節點都要當成不可信字串**。
   新增 Telegram 節點時照抄現有寫法：`parse_mode=HTML` ＋ 讀 `$json._tg`。
2. Telegram 節點的 400 一律去 `/api/v1/executions/<id>?includeData=true` 撈 `error.description`，
   不要信畫面上那句話。

## 2026-09-18｜搶到的客戶姓名帶 `*`，把 Telegram 搶單通知炸掉

**症狀**：n8n 執行失敗通知，卡在「Telegram 搶單通知」節點，`Bad request - please check your parameters`。

**成因**：那批 14 筆裡有一筆 KEIS 本來就打碼過的姓名「`*`小姐」。Telegram 節點沒設 `parseMode`，
預設當 Markdown 解析，孤立的 `*` 被當成粗體開始符號、找不到對應結尾 → 整則訊息被 Telegram 拒收。

**影響範圍小**：Telegram 節點排在流程最後，前面「寫入系統日誌」(Notion) 已經成功寫入，
搶單本身也已經拿到——只有這一則推播沒送出，不是資料遺失或搶單機制壞掉。

**修法**：`keis-grab-notify.json` 的 Telegram 節點 `additionalFields` 加 `"parseMode": "none"`，
乾脆關掉 Markdown 解析（這些訊息本來就沒用到粗體/斜體）。Public API 更新 + deactivate/activate。

**學到什麼**：任何把「自由文字欄位」（客戶姓名、備註、KEIS 打碼字串）直接塞進 Telegram/Markdown
訊息的節點，都該考慮關掉 parseMode，除非真的需要格式——不然遲早會被某個特殊字元炸到。

## 2026-09-15｜候選頁連打被永慶回截斷版 HTML，兩件好好的案子連兩班沒發

**症狀**：EG0530947／AA1036885 連兩班被判「候選 2 筆都不是這件」，整班沒發成品。
告警寫 `7520524:編號無`、`7509763:編號無`，名社路區價坪全 X。

**成因不是官網沒這兩件**。手動查證：兩件官網都在，`productID` 完全對得上——
`EG0530947 → house/7520524 = TC0530947`、`AA1036885 → house/7509763 = YC1036885`，案名也一字不差。

真正原因在 `永慶官網補資料`：候選迴圈 `for (const u of cands.slice(0, 8))` **中間沒有間隔**，
連續快打永慶官網。永慶被連打時會回「截斷版」HTML——約 190KB（正常 400KB），
JSON-LD 整塊不見。productID 讀不到 → 判定「不是這件」；備援評分也因為頁面不完整全部 X → 整件跳過。
本機重現：無間隔連抓兩頁，第一頁就回 190366 bytes 且無 JSON-LD；改成間隔 2 秒，8 次全部正常。

**另一個踩點**：永慶搜尋結果 JSON-LD 的**第一筆永遠是 `house/4308114`**（台北大安區店面 `YC953191`），
而且它的 `name` 會被填成「真正那件」的案名——所以光比對案名分不出真假，只能靠網址濾掉。

**修法**（Public API 更新 + deactivate/activate）：
1. 新增 `fetchPage()`：候選間隔 1.5 秒；抓回來沒有 JSON-LD 就當截斷，隔 4 秒重試一次
2. 濾掉 `house/4308114`；**濾完剛好剩 1 筆才採用**，不只 1 筆退回原本逐筆比對（濾網失效時最壞回到舊行為）
3. 社區名退搜那圈套用同一套
4. 告警把「抓取失敗」跟「官網真的沒這件」分開寫，看告警就知道要不要人工介入

**副作用是好的**：對永慶的請求從最多 9 次連發降到 2 次（重試最壞 3 次），降約 7 成。

**驗證**：用存下來的 HTML 離線跑新邏輯，兩件都命中、截斷偵測也正確。
線上要等 09-16 09:00 那班（排程為台灣時間 09/11/13/15/17/19）。

**注意**：`永慶官網補資料` 跑在 n8n 主機（Railway）上，用 `this.helpers.httpRequest`，
**不經過門市網路**。workflow 裡那條 cloudflare tunnel 只有 `Gemini 產文案` 在用。
手動查證時是從門市 IP 出去的，之後要測請用 n8n 上跑，別在門市電腦大量打。

**API 眉角**：Public API 的 PUT 會擋 `settings` 裡的 `binaryMode`／`availableInMCP`
（回 400 `must NOT have additional properties`），只能送 8 個合法欄位；
但那兩個設定在伺服器上不會因此被清掉，確認過還在。

## 2026-09-14｜公買搶單死掉是「零告警」狀態，已經這樣過了 20 天（例行健檢挖出來的）

**症狀**：沒有症狀——這是使用者問「我的工具跟工作鏈有什麼可以優化」時查出來的。
盤點時發現 `grab.py` 的存活監控**整條是斷的**，而且 09-04 那次 32 小時停機就是這個洞的證據。

**鏈路是怎麼斷的（三步，每一步當時都是對的）**：
1. 08-24：`.env` 拔掉 `KEIS_HEARTBEAT_WEBHOOK`（它指向已停用的 workflow，一路 404 噴假警報）。
2. 08-25：「KEIS 心跳檢查」workflow 被使用者判「用不到就刪了吧」，整支從 n8n 刪除。
3. 剩下的唯一防線＝`grab.py` 自己的計時器（心跳連續送不出去就直推 Telegram）——
   但那要**程序還活著**才叫得出來。「程序不在了」正好是它唯一叫不出來的狀況。

n8n 上還留著「KEIS 心跳接收（極簡）」，但它只有一個 webhook 節點、**後面什麼都沒接**，
心跳打進去就蒸發。看起來有監控，實際上沒有——比完全沒有更危險。

**09-04 的代價**：11:25 停到 09-05 19:53，32 小時，漏 3 筆合格名單（90328/90326/90324）。
當時的判斷是「開機捷徑被移出 shell:startup」，但真正該記的是**沒有任何東西會因此叫一聲**。

**怎麼修**：不養第二套監控——`ad_watchdog.py` 已經每小時跑、住在 n8n 外面、直推 Telegram，
在它裡面加第五道檢查：08:00~23:00 看 `%LOCALAPPDATA%\keis-grab\inventory.csv` 的修改時間，
超過 25 分鐘沒動就告警（6 小時內不重推、恢復時回一則）。刻意只讀本機檔案的 mtime：
不問 n8n、不問 Notion、不問 KEIS，而且放在 `main()` 的 try 外面，免得 Notion 連不上時
被那條 `return 0` 一起吃掉。

**順手修的**：`run.bat` 的重啟紀錄本來 144 行全都沒有時間戳（只寫 `grab.py exited`），
停機後還原不出經過，已補上 `%DATE% %TIME%` 和 `%ERRORLEVEL%`。

⚠️ **改 `run.bat` 的鐵律**：cmd.exe 是用**位元組位置**續讀 .bat 的。grab.py 還在跑時，
改動 `python grab.py` 那行以前的任何一個位元組（包括 LF→CRLF），cmd 在 python 結束後
會從半行續讀、直接掉出迴圈——等於親手製造這支啟動器要防的那場停機。這次的做法是用
python 讀 bytes 原地替換那一行、保住前綴 317 bytes 完全不變，並實測確認前綴沒動。
repo 的副本是 CRLF、桌面正在跑的是 LF，所以**不能直接 `cp` 覆蓋**。

**學到什麼**：
1. 「刪掉會噴假警報的監控」跟「這件事從此沒人看」是兩件事，刪的當下要問第二句。
2. 監控的**接收端**也要有東西在看。只留一個收得到但沒人讀的 webhook，比誠實地沒有更糟。
3. 自己監控自己的程序，永遠有「我不在了」這個盲區。要有一個不在同一個程序裡的東西看它。

## 2026-09-05｜臉書廣告沒跟著 KEIS 標籤更新：兩個「一次 100 筆」的天花板，把 5 筆降價/漲價整個藏起來

**症狀**：使用者說「KEIS 廣告追蹤上案件下架／降價／漲價的標籤都有，但我的臉書廣告沒有更新」。

**KEIS 那三個標籤本來就不是我們打的**：KEIS 每天凌晨（新增廣告後 15～20 秒也會跑一次）自己去抓
`adcase_url`（永慶官網連結）→ 連結死了就標 `url_invalid=true` + `案件下架`；活著就把官網現價寫進
`url_price`，跟建檔價 `adcase_price` 一比就標 `降價XX萬` / `漲價XX萬`。我們只讀不寫。
讀到之後：線 B（下架偵測）刪臉書貼文或勾 Notion「要重發」→ 線 C（重發輪替）刪舊文重發一篇新的。

**根因三個，全部實測過**：

1. **`GET /adcases?skip=0&limit=100` 沒翻頁**，當天 KEIS 上有 184 筆廣告（進行中 165 筆）。
   落在 100 名之外的完全看不到，而且程式判定是「廣告追蹤查無 #id（可能被手動刪掉）→ 略過」，
   **靜悄悄不告警**。當天被藏起來的：降價 700 萬（美濃農舍）、降價 80 萬、降價 52 萬、降價 20 萬、
   漲價 30 萬，還有 2 筆已標「案件下架」但貼文還掛在臉書上（AA1069194、PG0092558）。
   ⚠️ 使用者的直覺是「有標籤的會被置頂到第一頁」——那是 ad-tracker **網頁**排的，
   API 不帶排序參數回來的原始順序裡，降價 700 萬那筆排在**第 164 位**。別再用網頁的觀感推論 API。
2. **`查 Notion 已發布` 也是 `page_size: 100` 沒分頁**，而「已發布」有 171 筆。同一個天花板兩邊各踩一次。
3. **漲價從頭到尾沒接**：程式只 `includes('降價')`。臉書掛著比官網低的舊價＝廣告不實，
   比沒跟上降價更麻煩。

**還有一個附帶的無限迴圈**：AG1786755（高鐵植物園）KEIS 廣告追蹤標降價 70 萬（950→880），
但 **KEIS 物件資料上的總價還是 950**。線 C 讀的是物件價，於是原價重發、發完又把 950 寫回廣告追蹤、
KEIS 明天再標一次降價——重發次數已經累積到 3 次，每次都是同一個價格。

**怎麼修**（`yc-v3-removal.json` / `yc-v3-repost.json`，已 PUT + deactivate/activate 上線）：

1. 廣告清單改用 HTTP 節點內建分頁（qs `skip = $pageCount * 100`，`adcases.length < 100` 收尾），
   `判斷是否下架` 的 adMap 改吃 `$('KEIS 撈廣告清單').all()`——**這裡用 `.first()` 就是只拿第一頁**。
2. 新增 `挑要檢查的` 節點：先從整份廣告清單挑出「有標籤／url_invalid／已結束」的，
   再把那幾筆的 `KEIS廣告ID` 組成 Notion filter 的 `or`（上限 90 個條件，新到舊排，
   要砍先砍最老的），Notion 從「整份 171 筆」縮成「只查有事的 14 筆」。兩個天花板一起拆掉。
3. 漲價比照降價勾「要重發」；文案沿用舊版只換價格，**不寫「漲價」字樣**（使用者決定：
   漲價不是賣點，寫出來只會勸退買方，但價格一定要正確）。
4. **價格改成一律以永慶官網那一頁為準**（`永慶官網補資料`，線 A／線 C 共用那個節點各改一份）。
   一開始我判斷「官網價是爬蟲數字、不該覆蓋鎖死的總價萬」，**這個判斷是錯的**，使用者當場糾正：
   KEIS 的降價/漲價標籤本來就是拿官網現價比出來的，官網那頁又正是廣告點進去看的地方。
   實際打開 AG1786755 的官網頁看，寫得很清楚：`origin-price 950萬`（劃掉）→ `price 880萬`。
   作法：身分驗證（編號＋行政區＋佐證）通過後，從該頁 JSON-LD 讀 `"price"`，
   跟 KEIS 物件價差 ≥1 萬就覆蓋 `總價萬`，單價一併換成官網的（不然會留下用舊總價算的每坪單價，
   守門員會當成有出處放行）。**防呆**：差距超過一倍就不採用，只記一筆 `交叉檢查` 警告。
   `KEIS 價格沒跟上?` 保險絲保留，改當「兩邊都沒動卻被勾要重發」的最後防線。

   **教訓**：不要把「這個數字來源比較不可信」當成擋路的理由，先去看實際那一頁寫什麼。
   使用者說「官網跟 KEIS 本來就該一致」是對的——一致才是常態，這件是 KEIS 那邊沒跟上。
5. 沿用舊文案前先把上一版的「🔻 降價 …」整行拿掉——本機試跑抓到的：美術館那件先降 988→958、
   後來又漲回 988，不拿掉就會掛著「🔻 降價 30 萬（988 萬 → 988 萬）」；連續降兩次也會疊成兩行。

**上線前怎麼驗的**：沒有直接開排程等隔天，而是照 `n8n_dryrun_reminder.mjs` 的老路，
本機用同一組 API 把新邏輯跑一遍（腳本在 scratchpad），印出「會刪哪 2 篇、會勾哪 7 筆、
改完的文案前 4 行長怎樣」。上面第 5 點那個 bug 就是這樣抓到的，不是靠讀 code 讀出來的。

**學到什麼**：
- **凡是「一次最多 N 筆」的端點，沒寫分頁就是定時炸彈**，資料量跨過 N 的那天不會有人通知你。
  這條線上還有幾個同型的 `page_size: 100`／`limit=100`，看到就順手確認。
- **「查無資料 → 略過」是最危險的分支寫法**：它跟「真的沒事」長得一模一樣。至少要留 log 或計數。
- 使用者對系統的直覺通常來自 UI，UI 幫你排序、去重、置頂過；**API 回來的是原始資料**，

## 2026-08-29｜08:00 通道死掉後卡死 2 小時多沒重試：重開失敗時 tunnel=None 讓判活迴圈永遠判成活著

**症狀**：`Gemini 產文案` 又報一次一樣的錯（`incorrect host (domain) value`），執行紀錄
execution 7175。查 log 發現 08:00:39 就偵測到「行程還活著但外部打不通」並嘗試重開，
但 `start_tunnel()` 本身失敗（`getaddrinfo failed`，Cloudflare 邊緣一時解析不到，通常幾秒後
自己會好），之後日誌完全沒動靜到 10:09 才被這次告警發現——中間 2 小時多完全沒再重試。

**根因**：08-27 那次修的健康迴圈長這樣：
```python
dead = bool(tunnel and tunnel.poll() is not None)   # tunnel 失敗會被設成 None
...
if not dead: continue
```
`start_tunnel()` 失敗時 except 區塊把 `tunnel` 設成 `None` 再 `sleep(backoff)`，但下一輪迴圈
判斷「掛了沒」的條件寫成 `tunnel and tunnel.poll()...`——`tunnel` 是 `None` 時整條件短路成
`False`，永遠判斷「沒有掛」，於是重試邏輯完全不會再被觸發，卡死到有人手動介入為止。
跟 08-27 那次是不同 bug：08-27 修的是「怎麼偵測到死掉」，這次是「偵測到死掉、重開又失敗一次
之後，怎麼會忘記自己還沒重開成功」。

**怎麼修**（`scripts/codex-copy/server.py`）：`dead = tunnel is None or tunnel.poll() is not None`，
`tunnel` 是 `None` 直接算掛。手動 `taskkill` 掉卡住的 pythonw，重開服務，通道打回
`inspector-strips-settlement-posing.trycloudflare.com`，驗活（POST `{}` 回 400）確認正常。

**學到什麼**：「失敗後把狀態設成 sentinel（`None`/`null`）」跟「判斷是否需要重試」如果共用同一個
變數，很容易讓 sentinel 值意外滿足「一切正常」的條件——寫重試迴圈時，失敗分支要嘛立刻重試，
要嘛讓下一輪的判活條件明確涵蓋 sentinel 狀態，不要指望它「剛好」被涵蓋到。

## 2026-08-26｜通道殭屍化的真正成因：兩份 server.py 同時在跑

**症狀**：08-26 早上通道「殭屍化」——n8n 上的網址還在，但打過去是死的，重啟服務才恢復
（commit b03853c）。當時以為是 cloudflared 快速通道自己不穩。

**成因**：不是通道不穩，是**同時有兩份 server.py 在跑**。
開機捷徑（`啟動.vbs` → pythonw）已經跑了一份，使用者又雙擊 `啟動Codex文案.bat` 開了第二份
（console 的 python.exe）。兩份各自開一條 cloudflare 通道、各自把自己的網址寫回 n8n，
**後寫的贏**；輸的那條通道還活著卻沒有任何人管它，而 n8n 指的那條一旦它的 server 被關掉，
就變成「網址還在、後面沒人接」的殭屍狀態。

第二份為什麼開得起來？`ThreadingHTTPServer` 繼承自 `HTTPServer`，預設
`allow_reuse_address = True`（SO_REUSEADDR）。在 Windows 上這會讓第二個行程**搶得走**已經
被綁住的 port，不會像預期那樣噴 "address already in use"。所以兩份都以為自己啟動成功。

**怎麼修**：`server.py` 加 `class SingleInstanceServer(ThreadingHTTPServer)`，
`allow_reuse_address = False`，bind 失敗就印訊息並 `return 1` 直接退出，**不碰 n8n、不開通道**。
已實測：服務跑著時再跑一次 `python server.py --tunnel --port 8787` → 立刻退出 exit=1。

**學到什麼**：
1. **診斷行程時不要只查 `pythonw.exe`。** 這次一開始只列 pythonw 和 cloudflared，
   那個 console 的 `python.exe` 整整躲過三輪檢查，害我以為是自己改壞的。
   一律用 `Name='python.exe' OR Name='pythonw.exe' OR ...` 全查。
2. **殺行程的順序有差**：先殺 cloudflared 的話，server 的看門狗會在那個空檔補開一條新的，
   然後 server 才死 → 又多一條孤兒通道。**要殺就先殺 server，再掃 cloudflared。**
3. 「重啟就好了」是最貴的結論——它讓真正的成因多活了一天。

## 2026-08-25｜Telegram 告警上線當天就抓到兩個真的壞掉的東西

**背景**：這天把系統錯誤/FB發文失敗等告警從「寫日誌不推」改回主動推 Telegram（見 STATUS.md），
上線幾小時內就收到兩則真的告警——證明改對了方向，之前壞了都沒人知道。

**#1 線A發文卡在「Gemini 產文案」，錯誤「connection cannot be established, incorrect host」**：
`scripts/codex-copy/` 用 cloudflared 快速通道把 ChatGPT 訂閱接進 n8n（取代 Gemini 免費配額），
通道網址每次重開都會變。這次 cloudflared.exe 行程還活著、但通道本身已經死了（不是行程掛掉，
watchdog 的「行程結束才重開」判斷抓不到這種「活著但通道啞掉」的情況），n8n 指著死掉的網址當然連不上。
**修法**：`python scripts/codex-copy/server.py --revert` 先把 n8n 產文案節點指回原廠 Gemini API
解除卡關；要恢復 Codex 版文案品質，得手動 kill 掉舊的 pythonw.exe／cloudflared.exe（Claude 的
沙盒不給 kill process，只能人工做），再重跑 `啟動.vbs` 重新掛通道。
**學到什麼**：`server.py` 的 watchdog 只防得住「cloudflared 進程本身死掉」，防不住「進程還在、
通道啞掉」這種半死不活的狀態，之後如果常發生要考慮加一個對通道本身的健康檢查（打自己的網址）。
⚠️ 這個 workflow 的 deactivate+activate 有煞車窗口限制（09/11/13/15/17/19:00～:10 不要碰，
執行可能卡在 Wait 節點被打斷）——修這個之前特地等窗口過了才動手。

**#2 LINE 指令分流器「未知指令處理」節點噴 SyntaxError「Invalid or unexpected token」**：
節點的 jsCode 裡，訊息字串用單引號包住，但字串內容裡混進了**真的換行字元**（不是 `\n` 逃脫序列）——
JS 單引號字串不允許字面換行，所以只要真的觸發到這條「無效指令」分支就會炸。這條分支很少走到
（要打一個 router 認不得的指令才會進來），才會潛伏到現在才被抓到，而且是靠今天新開的 Telegram

## 2026-08-09 ─ Postgres volume 撐到 100%，n8n 全停約 1.5 小時（已修）

### 🔴 結論先寫：清 n8n 執行紀錄一律用 TRUNCATE，**絕對不要用 API 批次 DELETE**

Postgres 的 DELETE 會先寫交易日誌（WAL）才釋放空間。在一個已經 86% 滿的磁碟上批次刪
519 筆大檔紀錄，等於一邊要空間一邊先灌資料進去——**當場把剩下的 14% 吃光**，
Postgres 連啟動時寫 WAL 的空間都沒有，直接停機。

**症狀**：n8n API 全部 503；Railway 上 Postgres `Crashed`；volume 顯示 100%。
Deploy Logs 裡的關鍵句是
`FATAL: could not write to file "pg_wal/xlogtemp.26": No space left on device`
——每次重啟都跑完 32 秒資料復原、在最後寫入那步自殺，**全程不開放連線**，
所以「等它起來的瞬間搶進去清」這招不可能成功。

### 真正的成因（跟停機是兩件事，要分開看）

`靜默失敗巡邏` 每 30 分鐘抓一批執行紀錄的**完整內容**（`?includeData=true`，含廣告照片），
而全域 `SAVE_ON_SUCCESS=all` 又把它抓回來的這包大資料原封不動存回它自己的執行紀錄裡。
**等於每 30 分鐘把別人已經存過的照片再複製一份**，單次執行紀錄約 50 MB。

- 2026-08-02 量測：volume 914 MB（18%）
- 2026-08-09 量測：4.3 GB（86%），`execution_data` 單表 3510 MB
- 7 天漲 3.4 GB ≒ 每天 480 MB，**跟業務量、廣告則數完全無關**

修法是把**這一支** workflow 的 `saveDataSuccessExecution` 設成 `none`
（workflow 層級，不是全域——全域那條紅線沒動）。它本來就不需要回看自己的執行紀錄，
也沒有 Wait 節點，關掉零副作用。

### 怎麼救回來的（Hobby 方案，volume 加不了、備份是 Pro 限定）

1. Railway → Postgres → Settings → Custom Start Command 暫時改 `sleep infinity`
   （原值 `/bin/sh -c "unset PGPORT; docker-entrypoint.sh postgres --port=5432"`），
   容器才會停止自殺迴圈、SSH 進得去
2. `railway ssh --service Postgres`，把整個 `pg_wal`（721 MB）搬到容器暫存碟
   （`/` 有 523 GB 可用），原位置放符號連結接回去。
   **Postgres 官方支援 pg_wal 是 symlink**（`initdb --waldir` 就是這樣），不刪任何檔案、可逆
3. 用 **5433 埠**啟動（`pg_ctl -o '-p 5433'`）——避開 n8n Primary/Worker 一連上就開始寫
4. `TRUNCATE TABLE public.execution_entity CASCADE;` + `CHECKPOINT`
   → volume 100% → 5%，**資料一筆沒少**（redo 完整跑完）
5. 乾淨關閉 → **把 pg_wal 搬回 volume** → 最後才還原 Custom Start Command
   ⚠️ 順序不可顛倒：還原啟動指令會重建容器、暫存碟全毀，pg_wal 還在那邊就完蛋

### 學到什麼

- **不要在快滿的磁碟上做任何「先寫後放」的操作**。DELETE、VACUUM FULL、REINDEX 都是。

- **Hobby 方案沒有安全網**：volume 鎖死 5 GB 加不了，備份與還原是 Pro 限定。
  唯一的那份備份（495 MB，7/31 resize 時自動產生）點下去是鎖頭
- **當時完全沒有東西會叫**，是人工看 Railway 帳單才順手發現的。已補
  `ad_watchdog.py` 判斷四：Postgres 佔 volume 超過 70% 就繞過 n8n 直推 LINE
- 帳單本身不是問題：$7.14 裡 $7 是四個容器 24 小時開機的記憶體底薪，

`Unsupported delete request`，但整條執行狀態仍是「成功」（節點設了 `neverError`）。

**查證**：命中的是 YE0095535（`其他待辦` 早就記著的 3 筆 v2 舊資料之一，Notion 沒存
`粉專貼文連結`，`KEIS廣告ID` 也是空的）。那天它的 houseol 來源連結終於回 404，觸發下架判定。
Notion／KEIS 三邊事後核對**沒有壞資料**：Notion 正確標成「下架」，KEIS 本來就沒有這筆廣告，
沒有任何貼文被誤刪或誤留。

**成因**：`備妥刪文` 不管有沒有貼文連結，一律接去 `FB 刪貼文`。沒有 `fbPostId` 時
URL 變成 `graph.facebook.com/v21.0/`（空 ID），FB 當然回 `Unsupported delete request`。

不是資料事故，是雜訊源，放著不管會讓「靜默失敗巡邏」的訊噪比越來越差。

**怎麼修**：`yc-v3-removal.json` 加一個 IF 節點「有貼文可刪?」，`hasFbPost` 為否時直接跳過
`FB 刪貼文`、接去 `判定刪除結果`（該節點在無貼文分支本來就不讀 FB 回應，繞過去不影響邏輯）。
兩條分支各寫一版隔離測試驗證過（無貼文＝直接判定完成、有貼文＝迴歸正常），已部署
（deactivate+activate 過）。

**學到什麼**：`neverError` + 下游自己判斷成功失敗，是刻意的設計（單筆失敗不能拖垮整批），
但**不代表上游可以隨便亂打注定失敗的請求**——已知會失敗的呼叫要在源頭擋掉，不要靠下游
「反正看得懂這個錯誤」來擦屁股，不然巡邏機制遲早會被這類已知噪音淹沒，真正的新錯誤反而不顯眼。

### 🔴 最重要的一課（AA1070116）

**而那班的貼文其實建立成功了**（`is_published:true`、內容正確、15:10:28 上線），只是 API 回了 500。

所以「失敗就重發」會產生重複貼文、「失敗就撤列等下一班」會白白損失一班，**兩個都不對——
要先向 FB 反查「到底發出去了沒」**。查法（現有權杖就能做）：

- ❌ `GET /{page}/feed` → 400，權杖缺 `pages_read_engagement`
- ✅ `GET /{media_fbid}?fields=page_story_id` → **通**。發文流程是先上傳照片再組成貼文，
  照片有 `page_story_id` 就代表已經被組成一篇了；再 `GET /{page_story_id}?fields=is_published` 確認

**線 A 補救分支**：`FB 發貼文` 失敗 → `查照片是否已成篇` → `判斷補救方式` →
- ① 其實成功 → `確認貼文存在` → `真的已發布?` → `補回貼文結果` → **接回 `取貼文結果`**，
  後面的 Notion 標已發布／KEIS 廣告追蹤／LINE 通知全部照常跑完
- ② 確定沒發出去 → `重發一次`（此時重發零重複風險）→ 再失敗才撤列等下一班
- ③ 問不到 FB（照片讀取失敗／純文字貼文）→ 保守不重發，撤列等下一班

⚠️ **三線同步很重要**：那次中斷害 KEIS 廣告追蹤沒登記到，已人工補登（adcase `333341`）。
Notion／FB／KEIS 任一邊漏掉，之後線 B 下架時就刪不乾淨。

### 同批加的兩件事

- **`系統錯誤-LINE-告警.json`**（Error Trigger → 組訊息 → LINE Push），
  已掛成全部啟用中 workflow 的 `errorWorkflow`。訊息帶流程名／卡住的節點／錯誤內容／執行連結。
  ⚠️ **這支一定要保持 active**（實測：inactive 時完全不觸發）

  不撤列的話那個物件會被永遠跳過。撤掉後下一班會自動重抓同一件
