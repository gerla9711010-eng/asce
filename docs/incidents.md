## 貫穿全部事故的三句話

1. **流程回報成功 ≠ 事情做到了。** FB 回 500 貼文其實發出去了、n8n 執行 success 但節點錯誤被吞掉、
   LINE 回 500 通知沒送到——判斷「寫入到底成功沒」不要只看有沒有噴錯。
2. **保底邏輯只要「讓流程繼續」而不管「送出去的東西對不對」，它就是在把故障洗成看起來成功的樣子。**
   對外送出的東西一律要有形狀檢查。
3. **改完沒有在「真正在跑的環境」實地驗一次 = 沒改。** 補防護一律要有一次可觀察的實測
   （例如真的收到一則 LINE），不能只看程式碼寫對了。

## 2026-08-04 ─ 撞號比對到別間房子，樓層資料洩漏進已發布的土地廣告

**症狀**：使用者在 KEIS 廣告追蹤發現幾筆「官網連結失效」，順藤摸瓜找到 LA0067094
（大樹區 800坪土地，4800萬）的官網連結指到新北淡水的一間電梯大樓，而且**已經發出去的粉專貼文**
規格區寫著「🏢10/13」——一塊地寫樓層，是廣告不實。

**成因**：LA0067094 是 07-30 建的，那時 `永慶官網補資料` 只看「編號數字對上」就採用，
沒有行政區/坪數佐證。搜尋結果第 2 筆剛好是新北淡水 YE0067094（編號數字撞號），
比對命中錯的物件，該物件的樓層「10/13樓」被寫回 `src.樓層`，跟著進了 Gemini prompt，
直接印在發出去的文案上。08-01 已經加過「撞號防線」（行政區＋總價/坪數佐證）修過這個比對邏輯本身，
**但沒有回頭救這一筆已經產生、已經發布的舊資料**——防線只擋新案子，舊資料不會自動變乾淨。

**另一層漏洞**：就算比對邏輯完全正確，土地／車位本來就沒有「樓層」這個屬性，
`永慶官網補資料` 卻沒有依 `建物類型` 排除，任何配對到的官網頁只要抓得到樓層字樣就會照填，
這是即使配對正確也可能發生的獨立風險。

**怎麼修**：
1. 重新用現有的撞號防線邏輯手動比對 LA0067094，找到正確頁面
   `buy.yungching.com.tw/house/7357184`（TC0067094，行政區/總價/地坪/地段全部對上）。
2. 用臨時 workflow 借 FB Page Token，把已發布貼文的「🏢10/13」那行拿掉，改回乾淨版本。
3. Notion `粉專文案` 同步改正。
4. KEIS 廣告追蹤 `adcase_url` 改成正確頁面（`PUT /adcases/{id} {adcase_url}`），
   `url_invalid` 立刻變 `false`；`降價3702萬` 那個 status_tags 是 KEIS 自己排程算的，會在下次爬蟲跑完自動消掉。
5. **根治**：`永慶官網補資料`（`yc-v3-scan-publish.json` / `yc-v3-repost.json` 共用）加一道
   `isLand = /土地|農|廠|車位/.test(建物類型)` 檢查，土地/車位案不管官網比對到什麼，
   一律不把樓層/格局填回去。4 案例迴歸測試通過（土地案被擋、一般大樓案不受影響），已部署
   （deactivate+activate 過）。

**學到什麼**：
1. **修比對邏輯只保護未來的新資料，不會回頭清洗已經產生的舊資料**——這類 bug 要主動去查
   「這個邏輯上線之前建的案子」還有沒有殘留，不能假設修完就沒事了。
2. **「查得到就填」不等於「填了合理」**：光靠「有沒有比對成功」判斷該不該用一個欄位不夠，
   物件類型本身能不能有這個屬性，要單獨查，不能靠比對邏輯間接擋掉。

## 2026-08-03 ─ AI 回傳壞掉時硬發，粉專出現整包 JSON

**症狀**：粉專出現兩篇貼文，內文是一整包 `{"粉專主體":"…","社團主體":"…"}` 原始 JSON，
連 `\n` 都是字面上的反斜線 n。08-03 那篇是使用者自己看到的；
**07-30 那篇（左營榮總路 898 萬）在牆上掛了 4 天沒人發現**。

**成因**：Gemini 吐完合法 JSON 後又進入重複迴圈，再接一長串
`詳情看留言"} 留言索取"} 言"}…`，整段就 `JSON.parse` 不動。
而 `解析文案` 節點舊版的保底寫法是

```js
catch (e) { parsed = { 粉專主體: aiText.trim(), 社團主體: aiText.trim() }; }
```

設計意圖是「壞掉也要發」，實際效果是「壞掉就發垃圾」。
整條線 0 錯誤、FB 回 200、守門員放行（那串垃圾裡沒有數字，數字檢查看不到它），所有告警全部沉默。

**已修（三支 workflow，已部署）**

| 改在哪 | 改成什麼 |
|---|---|
| `解析文案+footer`（scan-publish／repost）| 三層：正常 parse → 正則單獨救回兩個欄位 → 都失敗就**留空**，絕不回填原始字串。另外輸出 `_copyRescued`、`_主體長度` |
| `數字守門員`（scan-publish／repost）| 加第 (3) 項「出貨前形狀檢查」：文案含 `"粉專主體"`／`"社團主體"`／字面 `\n`／``` ``` ``` 就擋；主體 <60 字或社團 <15 字也擋。走現成的「Notion 建草稿列 → LINE 守門員告警 → 換下一件」路徑，**不會炸掉整班** |
| `解析文案`（yc-fb-publish，沒有守門員）| 同樣的救援，救不回就直接 `throw`，交給錯誤告警流程 |
| `ad_watchdog.py` | 加判斷三：最近 30 筆「已發布」的文案含 JSON 殘骸就告警 |

四個案例都跑過（正常／重複垃圾（真實事故那份）／完全不是 JSON／被截斷），行為符合預期。

**已善後**：兩篇 FB 貼文用 Graph API 改回正確文案（貼文網址、觸及、按讚都保留）；
Notion 那兩列的 `粉專文案`／`社團文案` 也一起洗乾淨。

## 2026-07-27 ─ FB 回 500 不等於沒發出去

**而那班的貼文其實建立成功了**（`is_published:true`、內容正確、15:10:28 上線），只是 API 回了 500。

所以「失敗就重發」會產生重複貼文、「失敗就撤列等下一班」會白白損失一班，**兩個都不對——
要先向 FB 反查「到底發出去了沒」**。查法（現有權杖就能做）：

- ❌ `GET /{page}/feed` → 400，權杖缺 `pages_read_engagement`
- ✅ `GET /{media_fbid}?fields=page_story_id` → **通**。發文流程是先上傳照片再組成貼文，
  照片有 `page_story_id` 就代表已經被組成一篇了；再 `GET /{page_story_id}?fields=is_published` 確認

**線 A 補救分支**：`FB 發貼文` 失敗 → `查照片是否已成篇` → `判斷補救方式` →
- ① 其實成功 → `確認貼文存在` → `真的已發布?` → `補回貼文結果` → **接回 `取貼文結果`**，
  後面的 Notion 標已發布／KEIS 廣告追蹤／LINE 通知全部照常跑完
- ② 確定沒發出去 → `重發一次`（此時重發零重複風險）→ 再失敗才撤列等下一班
- ③ 問不到 FB（照片讀取失敗／純文字貼文）→ 保守不重發，撤列等下一班

⚠️ **三線同步很重要**：那次中斷害 KEIS 廣告追蹤沒登記到，已人工補登（adcase `333341`）。
Notion／FB／KEIS 任一邊漏掉，之後線 B 下架時就刪不乾淨。

### 同批加的兩件事

- **`系統錯誤-LINE-告警.json`**（Error Trigger → 組訊息 → LINE Push），
  已掛成全部啟用中 workflow 的 `errorWorkflow`。訊息帶流程名／卡住的節點／錯誤內容／執行連結。
  ⚠️ **這支一定要保持 active**（實測：inactive 時完全不觸發）
- **線 A `FB 發貼文` 開錯誤輸出**：發文失敗 → `Notion 撤銷待發列`（PATCH `archived:true`）→ LINE。
  為什麼要撤列：判重只看案件編號不看狀態，而待發列是發文前就建的，
  不撤列的話那個物件會被永遠跳過。撤掉後下一班會自動重抓同一件
