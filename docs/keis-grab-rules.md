## 一、什麼叫「我要的名單」

**一句話：建檔之後、第一次進到池子、而且條件符合的。**

三個條件要同時成立，缺一不可：

| # | 條件 | 判定方式 |
|---|---|---|
| 1 | **是新的**（沒被別人拿過） | 這個編號從沒出現在 `inventory.csv` 總帳裡 |
| 2 | **搶得到**（狀態可申請） | `status = Available` |
| 3 | **符合篩選**（下面第三節那五條） | 縣市／電話／類型／預算／建檔天數 |

### 「新的」到底怎麼判 — 只看一件事

**看這個編號在總帳裡有沒有紀錄，不看別的。**

| 總帳狀態 | 判定 | 搶不搶 |
|---|---|---|
| 完全沒紀錄 | 剛進池的新貨 | ✅ 搶 |
| 有紀錄，來源=新出現、第一次看到就是 Available | 我們親眼看著它進池 | ✅ 搶 |
| 有紀錄，曾冷卻=Y | 二手貨（被人拿過又回鍋） | ❌ 不搶 |
| 有紀錄，來源=基準快照 | 建總帳之前就在池子裡，來歷不明 | ❌ 不搶 |

### ⚠️ 三個最容易搞錯的地方

**1. 建檔日期舊 ≠ 二手貨。**（2026-08-04 我自己搞錯過）

`建檔時間` 是**門市值班人員接到電話建檔的時刻**，不是進池時刻。
KEIS 每天早上 08:01 放一批貨，裡面混著建檔好幾天前的存貨，照編號順序慢慢放。

> 實證：08-03 早上放的是建檔 07-27 的、08-04 早上放的是建檔 07-28 的。
> 那些是**貨真價實的新名單**，該搶。

**2. 二手貨長什麼樣：第一次看到它時狀態就是 `CoolingDown`。**

`CoolingDown` = 已被別人申請、進入 7 天排他倒數（網站 UI 顯示「已被申請(剩餘N天)」）。
7 天到期後它會變回 `Available` 而且 `app_time` 被清空 → **從 API 單一快照看，二手貨跟新貨長得一模一樣**。
所以只能靠總帳擋，沒有別的辦法。

**3. 池子裡 1000+ 筆 `Available` 絕大多數是輪過好幾手的二手貨，不是庫存。**
不要想著「收盤拿剩餘配額去撿」。

## 二、看哪裡（可視範圍）

| 項目 | 值 | 說明 |
|---|---|---|
| 搶單窗口 | 編號最大的前 **70** 筆 | **只從這裡挑要搶的，永遠不從全池掃描挑** |
| 排序 | `summary_id` 由大到小 | 已於 2026-08-04 直接打 API 驗證 |
| 全池掃描 | 每小時一次、輪流換帳號 | **只寫 `inventory.csv` 稽核，絕不進搶單流程** |

### ⚠️ 為什麼是這樣

- **窗口本身就是「只搶新單」的把關**。池子照編號由大到小排，最前面幾乎必然是剛進池的。
- **拉大窗口 = 拆掉把關**。2026-07-23 試過拉到 100 + 全池掃描，重啟後 10 分鐘就誤搶一筆建檔半年前的老案。
- 70 是 2026-08-03 從 40 調上來的（那天一次進 32 筆新貨，2 筆合格的排不進 40 筆窗口漏掉）。
  **沒有直接衝到上限 100**：那是 `PAGE_SIZE`，超過會回 0 筆；而且熱門時段每 5 秒查一次，用 100 等於每次付最大流量成本。

## 三、篩選條件（五條，照這個順序判）

判斷順序有意義：**先命中的就是紀錄下來的原因**。

| 順序 | 條件 | 規則 |
|---|---|---|
| 1 | **狀態** | 不是 `Available` 就不搶 |
| 2 | **縣市** | 只搶高雄市。**空白視為高雄市，放行**；明確填其他縣市就排除 |
| 3 | **電話** | **只搶手機**（09 開頭）。市話、空號一律不搶 |
| 4 | **類型** | 排除**公寓**。空白或 `-` 放行 |
| 5 | **預算** | 預算**上限**低於 **1000 萬**不搶。空白（0）放行 |
| 6 | **建檔天數** | 建檔超過 **10 天**不搶 |

### ⚠️ 為什麼是這樣

- **縣市空白放行**是 2026-08-03 改的：空白多半是漏填，之前被誤擋掉 9 筆。
  **代價**：空白欄位如果其實是外縣市案子會被誤搶，事後也分不出來——這是已知並接受的取捨，不是 bug。
- **建檔日期只當否決權**（太舊 → 一定不是新單），**不當認可權**（新 → 不代表是新單）。
- 機器人數學上不可能搶到市話（只放行 09 開頭），所以 `grabbed.csv` 裡任何非手機都是「回查補回」路徑進來的，不是機器人搶的。

## 四、什麼時候看（全天分層輪詢）

| 時段 | 每幾秒查一次 | 用途 |
|---|---|---|
| **07:00 – 10:00** | 5 秒 | 早上熱門檔（KEIS 約 08:01 放貨） |
| 10:00 – 17:30 | 60 秒 | 白天一般監控 |
| 17:30 – 24:00 | 5 秒 | 傍晚第二波 |
| 00:00 – 07:00 | 1800 秒 | 門市每晚固定斷網，等同停止 |

### ⚠️ 早上起點 07:00 不要改回 07:30

輪詢間隔是**睡覺前算一次**，睡下去不會重算。
門市網路固定約 07:22 恢復，恢復那一輪若還落在深夜檔就會拿到 1800 秒，一路睡到 07:52
→ 熱門檔開頭 22 分鐘全空。2026-07-23～26 連續四天都這樣。

## 五、配額與分工

| 項目 | 值 |
|---|---|
| 帳號 | 薛力瑜、周珈伊、許育禎（3 個） |
| 每個帳號配額 | 7 筆／7 天滾動 |
| 合計 | 21 筆 |
| 分工方式 | 依各帳號剩餘配額分配，不同帳號拿不同名單、不撞單 |

**搶到就立刻寫檔**（CSV + Notion），不等整批。半路逾時已搶到的不會弄丟，沒搶成的下一輪自動補搶。

⚠️ `status=DutyAssigned` 的名單是 KEIS 直接指派給帳號的（不經過公開池、**不吃配額**），
**不算我們的戰果**。判定：`status == "Applied"` 且有 `app_time` 才算是我們搶的。

## 六、每天會收到的 LINE

| 訊息 | 何時 | 內容 |
|---|---|---|
| 🎯 搶到通知 | 每次搶到 | 全新名單／符合條件／實際拿到 + 剩餘配額 + 名單明細 |
| ⚠ 漏接告警 | 即時 | 符合條件、我方沒申請過，卻被別人拿走 |
| 🚨 API 欄位變動 | 每天最多一次 | KEIS 改版砍欄位（見下節） |
| ⚠ 總帳讀壞 | 發生時 | inventory.csv 讀不出來，已重建基準 |
| 💓 心跳斷線 | n8n 判定 | 超過 2 小時沒心跳（檢查時段避開每晚斷網） |
| 打「戰果」 | 你主動查 | 查 Notion 回今天的名單 |

**跨日結算不推 LINE**，寫進本機 `daily_summary.csv`（欄序：日期,新名單,符合條件,搶到,補回）。

## 七、自動看門的四道防線

| # | 看什麼 | 沒過會怎樣 |
|---|---|---|
| 1 | **API 欄位體檢**（每小時） | KEIS 砍掉搶單用的欄位 → 🚨 LINE。砍非關鍵欄位 → ℹ️ 告知 |
| 2 | **漏接偵測**（即時） | 符合條件卻沒申請、又被別人拿走 → LINE 點名該筆 |
| 3 | **總帳健檢**（開機時） | 讀壞 → 備份原檔 + 重建基準（寧可少搶不誤搶）+ LINE |
| 4 | **心跳**（每 10 分鐘） | 門市電腦死了 → n8n 告警（檢查時段避開每晚斷網） |

**設計原則：寧可少搶，也不要誤搶或靜悄悄壞掉。**

## 八、資料存在哪

| 檔案 | 位置 | 內容 |
|---|---|---|
| `inventory.csv` | `%LOCALAPPDATA%\keis-grab\` | 名單總帳（二手判定的唯一依據） |
| `appearances.csv` | 同上 | 每個編號的首次出現時刻（append-only，不會被覆蓋） |
| `api_schema.json` | 同上 | API 欄位基準快照 |
| `grabbed.csv` | `桌面\keis\` | 搶到的名單（唯一真相，Notion 對帳靠它） |
| `daily_summary.csv` | 同上 | 每日結算一行 |
| `logs\YYYY-MM-DD.log` | 同上 | 每天一個檔，留 50 天 |

⚠️ **總帳刻意放本機不放 OneDrive**：OneDrive 同步曾把 CSV 弄成殺不死的損毀檔。

⚠️ **在 Notion 手動刪名單沒有用**：對帳拿 `grabbed.csv` 當唯一真相，刪掉會被補回來。
要讓一筆退場，改「聯絡狀態」（無效空號／已聯絡…），資料留著但不進提醒名單。

## 九、改動須知

1. **改完 `grab.py` 要重啟才生效**。桌面 `run.bat` 有自動重啟迴圈，殺掉 python 程序後它會自己用新版起來（約 1～3 分鐘）。
2. **桌面和 repo 兩份都要改**。真正在跑的是桌面 `C:\Users\user\OneDrive\桌面\keis\grab.py`。
3. **改 `.env` 兩邊都要改**。2026-08-02 踩過：token 只加進 repo，桌面沒有，防線形同虛設。
4. **寫測試時先把 `grab.LOG_DIR` 改到暫存資料夾**。測試 import 真的 `grab.py` 會沿用它的
   `LOG_DIR`，log 直接寫進當天的正式紀錄——2026-08-04 就這樣在正式 log 裡留下一則假的
   「🚨 連續 3 天掛零」告警，事後還要回頭清。同理 `BACKUP_DIR`、`_LOCAL`（用 `LOCALAPPDATA` 環境變數改）。
